# todoapp — migraciones con Flask

## Puesta en marcha

PostgreSQL corre **en Docker**. La aplicación Flask corre en el host, contra el puerto
que el contenedor publica.

```
┌─ host ──────────────────────┐      ┌─ Docker ─────────┐
│  venv + Flask  :3000        │─────▶│  postgres:16     │
│  flask db upgrade           │ 5432 │  volumen datos_pg│
└─────────────────────────────┘      └──────────────────┘
```

### 1. Levantar la base de datos

```bash
cp .env.example .env          # ajustar la contraseña si hace falta
docker compose up -d db
docker compose ps             # esperar a que diga  healthy
```

El contenedor crea la base `todoapp` en el primer arranque, con las variables
`POSTGRES_DB`, `POSTGRES_USER` y `POSTGRES_PASSWORD`. **No hace falta `createdb`.**

### 2. Instalar la aplicación

```bash
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt

export DATABASE_URL='postgresql://postgres:abc@localhost:5432/todoapp'
export FLASK_APP=app.py
```

> El host es `localhost` porque la app corre **fuera** de Docker y el contenedor
> publica el puerto 5432. Si la app también corriera en Docker, el host sería `db`.

### 3. Migraciones

```bash
flask db init        # una sola vez: crea migrations/
flask db migrate     # genera el script comparando modelos y base
# LEER el archivo en migrations/versions/ antes de seguir
flask db upgrade     # aplica
```

### 4. Arrancar

```bash
python app.py        # http://localhost:3000
```

## Comandos de Docker que vas a usar

```bash
docker compose up -d db              # levantar la base
docker compose ps                    # estado y healthcheck
docker compose logs -f db            # logs de PostgreSQL
docker compose stop db               # detener sin borrar nada
docker compose down                  # bajar (los datos quedan en el volumen)
docker compose down -v               # bajar y BORRAR el volumen ← se pierden los datos
```

### Abrir psql dentro del contenedor

```bash
docker compose exec db psql -U postgres -d todoapp
```

```sql
\dt                 -- todos + alembic_version
\d todos            -- columnas de la tabla
SELECT * FROM alembic_version;
\quit
```

### Recrear la base desde cero

Reemplaza al `dropdb` / `createdb` del host:

```bash
docker compose down -v        # borra el volumen con todos los datos
docker compose up -d db       # arranca limpio, con la base recién creada
flask db upgrade              # vuelve a aplicar todas las migraciones
```

## Verificar

```bash
docker compose exec db psql -U postgres -d todoapp -c "\dt"
flask db current
flask db history
```

## Opción B: todo en Docker

Si además quieres que la aplicación corra en un contenedor:

```bash
docker compose --profile full up -d --build
docker compose logs -f web
```

Diferencias respecto de la opción anterior:

| | App en el host | App en Docker |
|---|---|---|
| Host de la base | `localhost` | `db` (nombre del servicio) |
| Migraciones | a mano, con `flask db upgrade` | las aplica `entrypoint.sh` al arrancar |
| Comandos `flask db` | directo en la terminal | `docker compose exec web flask db ...` |

`entrypoint.sh` ejecuta `flask db upgrade` **antes** de iniciar la app, y el
`depends_on: condition: service_healthy` garantiza que PostgreSQL ya esté aceptando
conexiones cuando eso ocurre.

## Agregar una nueva migración

Ejemplo completo de una modificación a la base de datos durante el desarrollo:
agregarle a cada tarea una **fecha límite** y una **prioridad**.

### 1. Modificar el modelo

En `app.py`, la clase `Todo` queda así:

```python
class Todo(db.Model):
    __tablename__ = 'todos'

    id = db.Column(db.Integer, primary_key=True)
    description = db.Column(db.String(), nullable=False)
    completed = db.Column(db.Boolean, nullable=False, default=False)
    due_date = db.Column(db.Date, nullable=True)                      # nueva, opcional
    priority = db.Column(db.Integer, nullable=False, default=1)       # nueva, obligatoria
```

### 2. Generar la migración

```bash
export FLASK_APP=app.py
flask db migrate -m "agrega due_date y priority a todos"
```

```
INFO  [alembic.autogenerate.compare] Detected added column 'todos.due_date'
INFO  [alembic.autogenerate.compare] Detected added column 'todos.priority'
  Generating migrations/versions/c8a1d94b2e7f_agrega_due_date_y_priority.py ... done
```

La base **todavía no cambió**: solo se escribió el archivo.

### 3. Leer el archivo generado

`migrations/versions/c8a1d94b2e7f_agrega_due_date_y_priority.py`:

```python
revision = 'c8a1d94b2e7f'
down_revision = 'f17b00f4cc63'     # se encadena a la migración anterior


def upgrade():
    # ### commands auto generated by Alembic - please adjust! ###
    op.add_column('todos', sa.Column('due_date', sa.Date(), nullable=True))
    op.add_column('todos', sa.Column('priority', sa.Integer(), nullable=False))
    # ### end Alembic commands ###


def downgrade():
    op.drop_column('todos', 'priority')
    op.drop_column('todos', 'due_date')
```

`due_date` está bien: es `nullable=True`, las filas existentes quedan en `NULL`.

`priority` **va a fallar**, por lo mismo que pasó con `completed`: es `NOT NULL` y las
tareas que ya están cargadas no tienen valor.

```bash
flask db upgrade
```

```
psycopg2.errors.NotNullViolation: column "priority" of relation "todos"
contains null values
```

### 4. Ajustar la migración a mano

Reemplazar el `upgrade()` por la versión en tres pasos:

```python
def upgrade():
    # due_date es opcional: el autogenerado sirve tal cual
    op.add_column('todos', sa.Column('due_date', sa.Date(), nullable=True))

    # priority es obligatoria → esquema, datos, restricción
    # 1. agregar como opcional
    op.add_column('todos', sa.Column('priority', sa.Integer(), nullable=True))
    # 2. rellenar las filas que ya existían
    op.execute('UPDATE todos SET priority = 1 WHERE priority IS NULL;')
    # 3. recién ahora exigir el valor
    op.alter_column('todos', 'priority', nullable=False)


def downgrade():
    op.drop_column('todos', 'priority')
    op.drop_column('todos', 'due_date')
```

La alternativa de una sola línea es un `DEFAULT` real en la base, que le da valor a las
filas existentes en el mismo `ALTER TABLE`:

```python
op.add_column('todos',
    sa.Column('priority', sa.Integer(), nullable=False, server_default='1'))
```

> `default=1` en el modelo lo aplica **Python al insertar**.
> `server_default` es un `DEFAULT` en **PostgreSQL**. La migración necesita el segundo.

### 5. Ver el SQL antes de aplicarlo

```bash
flask db upgrade --sql
```

```sql
ALTER TABLE todos ADD COLUMN due_date DATE;
ALTER TABLE todos ADD COLUMN priority INTEGER;
UPDATE todos SET priority = 1 WHERE priority IS NULL;
ALTER TABLE todos ALTER COLUMN priority SET NOT NULL;
```

### 6. Aplicar y verificar

```bash
flask db upgrade
```

```
INFO  [alembic.runtime.migration] Running upgrade f17b00f4cc63 -> c8a1d94b2e7f
```

```bash
flask db current
# c8a1d94b2e7f (head)

flask db history
# f17b00f4cc63 -> c8a1d94b2e7f (head), agrega due_date y priority a todos
# <base> -> f17b00f4cc63, agrega completed a todos

docker compose exec db psql -U postgres -d todoapp -c "\d todos"
#  id          | integer | not null
#  description | character varying | not null
#  completed   | boolean | not null
#  due_date    | date    |
#  priority    | integer | not null
```

### 7. Probar la vuelta

```bash
flask db downgrade      # vuelve a f17b00f4cc63: las dos columnas desaparecen
flask db upgrade        # y vuelven
```

Si el `downgrade` falla, la migración está incompleta aunque el `upgrade` haya funcionado.

### 8. Versionar

```bash
git add app.py migrations/versions/c8a1d94b2e7f_agrega_due_date_y_priority.py
git commit -m "agrega due_date y priority a todos"
```

El modelo y su migración van en el **mismo commit**. Así, quien clone el repositorio y
ejecute `flask db upgrade` obtiene exactamente este esquema.

### Resumen del ciclo

| # | Paso | Comando |
|---:|---|---|
| 1 | Sincronizar | `git pull` y `flask db upgrade` |
| 2 | Editar el modelo | en `app.py` |
| 3 | Generar | `flask db migrate -m "mensaje"` |
| 4 | **Leer y ajustar** | abrir el archivo en `migrations/versions/` |
| 5 | Ver el SQL | `flask db upgrade --sql` |
| 6 | Aplicar | `flask db upgrade` |
| 7 | Probar la vuelta | `flask db downgrade` y volver a `upgrade` |
| 8 | Commit | modelo y migración juntos |

## Notas

- No se usa `db.create_all()`: las tablas las crea la migración inicial.
- La URI va con `postgresql://`, no `postgres://`.
- `migrations/versions/f17b00f4cc63_agrega_completed.py` es el ejemplo de la
  corrección en tres pasos para agregar una columna NOT NULL sobre datos existentes.
- Toda la carpeta `migrations/` va al repositorio. El archivo `.env` **no**.
- PostgreSQL corre en Docker; los datos viven en el volumen `datos_pg` y sobreviven
  a `docker compose down`. Solo `docker compose down -v` los borra.
- Las migraciones se ejecutan siempre desde donde esté la app: en el host si corre en
  el host, o con `docker compose exec web flask db upgrade` si corre en un contenedor.
