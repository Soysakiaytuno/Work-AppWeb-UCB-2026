## Flask Todo App

A complete walkthrough of this project, from an empty folder to a production deployment behind nginx.

## 1. What we are building

A todo application with two deployment modes.

Development, where you edit code and see changes immediately:

```
browser :5001 ──> Flask dev-ish container ──> Postgres :5432
```

Production, where nginx fronts a real WSGI server:

```
browser :8080 ──> nginx ──> gunicorn ──> Flask ──> Postgres
(public) (internal) (internal only)
```

The two modes share the same application code, the same image, and the same migrations. Only the composition differs.

## 2. Prerequisites

You need Docker Desktop and Python 3.11 or newer. Verify both:

```
docker --version && docker compose version && python3 --version
```

Everything else, including Postgres, runs inside containers. You never install a database on your laptop.

## 4. Stage 2: The application factory

Lets create a application factory for better code. Note that we are not using any app.py or main.py.


app/extensions.py holds the extension objects, unattached to any app:

```
from flask_migrate import Migrate
from flask_sqlalchemy import SQLAlchemy
db = SQLAlchemy()
migrate = Migrate()
```

app/__init__.py builds the app:

```
from flask import Flask
from .config import Config
from .extensions import db, migrate
def create_app(config_class=Config):
app = Flask(__name__)
app.config.from_object(config_class)
db.init_app(app)
migrate.init_app(app, db)
from . import models
from .routes import bp as todos_bp
app.register_blueprint(todos_bp)
# You may add severals blueprint when the app is bigger.
return app
```

## Why a factory instead of a module-level app = Flask(__name__)

Four concrete reasons:

Testing. You can build a fresh app per test with a different config, such as a throwaway database, and tests stop leaking state into each other. With a global app you get one app for the whole test suite.

Configuration. Development, testing, and production each pass a different config class into the same function. Nothing is hardcoded at import time.

Circular imports. models.py needs db . If db lived in __init__.py next to the app, then models importing from __init__ while __init__ imports models deadlocks. Putting db in its own module breaks that cycle.

This is why extensions.py exists at all.

Import side effects. With a global app, importing anything from your package creates an app and connects to a database. That makes tooling, shell


sessions, and Alembic behave in surprising ways.

## Two details worth understanding

The imports of models and routes sit inside the function, not at the top of the file. They must run after db.init_app(app) , and doing it here also avoids the circular import: routes.py imports from extensions.py , never

from __init__.py .

Importing models looks pointless since the name is never used. It is not. The import is what executes the class definitions, which registers the tables on SQLAlchemy's metadata. Without it, flask db migrate generates an empty migration. A linter will flag the unused import; silence it with a # noqa: F401 comment rather than deleting it.

## Configuration from the environment

```
app/config.py :
import os
from dotenv import load_dotenv
load_dotenv()
class Config:
SECRET_KEY = os.environ.get("SECRET_KEY", "dev-secret-change-me")
SQLALCHEMY_DATABASE_URI = os.environ.get(
"DATABASE_URL",
"postgresql://todo:todo@localhost:5432/todoapp",
)
SQLALCHEMY_TRACK_MODIFICATIONS = False
```

Config comes from the environment, never from committed code. The same image then runs in development, staging, and production with different variables. A password in config.py ends up in git history forever.

The development defaults here are a deliberate convenience. In production, compose requires the real values and refuses to start without them, which you will see in stage 8. Defaults are for developer ergonomics; production should fail loudly rather than silently run with dev-secret-change-me .

## 5. Stage 3: Blueprints explained

A blueprint is a group of routes, templates, and static files that you define separately from the application and attach to it later.


```
from flask import Blueprint, flash, redirect, render_template, request, url_for
from .extensions import db
from .models import Todo
bp = Blueprint("todos", __name__)
@bp.route("/")
def index():
todos = Todo.query.order_by(Todo.completed.asc(), Todo.created_at.desc()).all()
return render_template("index.html", todos=todos)
@bp.route("/todos", methods=["POST"])
def create():
title = request.form.get("title", "").strip()
if not title:
flash("Title is required.", "error")
return redirect(url_for("todos.index"))
db.session.add(Todo(title=title, description=...))
db.session.commit()
flash("Todo created.", "success")
return redirect(url_for("todos.index"))
```

And it is attached in the factory:

```
app.register_blueprint(todos_bp)
```

## The mental model

Think of a blueprint as a recorded set of instructions. When you write @bp.route(...) , nothing is registered anywhere yet. The blueprint just records "when someone attaches me to an app, add this route." The recording is

replayed when register_blueprint runs.

That deferral is exactly what makes the factory pattern work. Routes are defined at import time; they are bound to a specific app instance later, and can be bound to several different app instances.

## What blueprints buy you

Modularity. A real application groups routes by feature: auth , admin , api , todos . Each becomes its own blueprint in its own module. This app has one blueprint because it has one feature, but the structure is already in place for a second.


Namespaced endpoints. The blueprint is named todos , so its endpoints are

todos.index , todos.create , todos.edit . That is why templates say url_for('todos.index') rather than url_for('index') . The namespace means

an admin blueprint can also have an index view with no collision.

URL prefixes. A future API blueprint attaches under a path without rewriting any of its route decorators:

```
app.register_blueprint(api_bp, url_prefix="/api/v1")
```

Blueprint-scoped hooks. Middleware that should apply to one feature only, such as requiring login for everything under /admin , attaches to that blueprint rather than the whole app:

```
@admin_bp.before_request
def require_login():
...
```

## Always use url_for , never hardcoded paths

Templates in this app reference routes like this:

```
<form method="post" action="{{ url_for('todos.create') }}">
<a href="{{ url_for('todos.edit', todo_id=todo.id) }}">Edit</a>
```

Not action="/todos" . url_for looks the URL up from the endpoint name, so changing a route's path in one place updates every link automatically, and it handles the url_prefix case correctly. Hardcoded paths break silently.

## Adding a second blueprint

The pattern scales without touching existing code. Create app/api.py :

```
from flask import Blueprint, jsonify
from .models import Todo
api_bp = Blueprint("api", __name__)
@api_bp.get("/todos")
def list_todos():
return jsonify([
{"id": t.id, "title": t.title, "completed": t.completed}
for t in Todo.query.all()
])
```


Register it in the factory with a prefix:

```
from .api import api_bp
app.register_blueprint(api_bp, url_prefix="/api/v1")
```

The HTML routes are untouched, and the new endpoints live at /api/v1/todos under the endpoint name api.list_todos .

## Template inheritance

base.html defines the shared page shell with named blocks, and the other templates fill them in:

```
{% extends "base.html" %}
{% block content %}
...
{% endblock %}
```

This keeps the layout in one file. Flash messages are rendered once in base.html , so every page gets them.

```
Autoescaping is on by default in Jinja for .html files. Rendering {{ todo.title }} escapes any HTML a user typed, which is what prevents
```


cross-site scripting. Never reach for the |safe filter on user-supplied content.

## Destructive actions use POST, not GET. Delete is a form with method="post" , not a link:

```
<form method="post" action="{{ url_for('todos.delete', todo_id=todo.id) }}">
<button type="submit">Delete</button>
</form>
```

A <a href="/todos/1/delete"> would be followed by browser prefetchers, link scanners, and crawlers. GET must be safe and side-effect-free.

POST then redirect. Every mutating view ends with

redirect(url_for(...)) rather than rendering a page directly. Without it, a browser refresh resubmits the form and creates a duplicate todo.

Missing here: CSRF protection. This app has no CSRF tokens, so any site could submit its forms on behalf of a logged-in user. There are no users or sessions yet, so nothing is currently at risk, but add Flask-WTF and wrap the app in CSRFProtect before you add authentication.

docker-compose.yml , database service:

```
services:
db:
image: postgres:16-alpine
environment:
POSTGRES_USER: ${POSTGRES_USER:-todo}
POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:-todo}
POSTGRES_DB: ${POSTGRES_DB:-todoapp}
ports:
- "${POSTGRES_PORT:-5432}:5432"
volumes:
- postgres_data:/var/lib/postgresql/data
healthcheck:
test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER:-todo} -d ${POSTGRES_DB:-todo
interval: 5s
timeout: 5s
retries: 10
volumes:
postgres_data:
```


Start it and confirm it is healthy:

```
docker compose up -d db
docker compose ps
```

Pin the image tag. postgres:16-alpine , not postgres:latest . With

latest , a rebuild months from now silently gives you Postgres 17 and a data

directory the new version refuses to open.

Named volumes for data. Without postgres_data , every docker compose down destroys your database. The volume survives container removal; only

docker compose down -v deletes it.

Healthchecks, not sleeps. The app service uses:

```
depends_on:
db:
condition: service_healthy
```

Plain depends_on waits for the container to start, which is not the same as Postgres being ready to accept connections. Without the healthcheck the app starts, tries to connect a second too early, and crashes. This is the most common Docker Compose mistake with databases.

## 8. Stage 6: Migrations

Migrations are how your database schema changes over time in a way you can review, version, and roll back.

```
Why not db.create_all()
```

Many tutorials use db.create_all() . It builds tables that do not exist and then does nothing forever. It will not add a column, change a type, or add an index to an existing table. The moment your model changes, your schema and your code disagree, and there is no upgrade path. Use migrations from day one.

## Initialize and generate

Run these inside the container so they talk to the compose database:

```
docker compose run --rm web flask db init
docker compose run --rm web flask db migrate -m "create todos table"
```


The first creates migrations/ . The second inspects your models, compares them to the live database, and writes a revision file:

```
revision = '18ad00069a11'
down_revision = None
def upgrade():
op.create_table('todos',
sa.Column('id', sa.Integer(), nullable=False),
sa.Column('title', sa.String(length=200), nullable=False),
...
sa.PrimaryKeyConstraint('id')
)
def downgrade():
op.drop_table('todos')
```

## Apply

```
docker compose run --rm web flask db upgrade
```

In this project you rarely run that by hand, because entrypoint.sh runs it on every container start.

## The daily loop

```
\# 1. Edit app/models.py
# 2. Generate a migration
docker compose run --rm web flask db migrate -m "add priority to todos"
# 3. READ the generated file
# 4. Apply it
docker compose run --rm web flask db upgrade
```

Always read the generated migration before applying it. Autogenerate is good at detecting added and dropped tables and columns. It is unreliable at detecting renames: renaming title to name is usually emitted as "drop title , add name ", which silently destroys every row's data. Edit the

revision to use op.alter_column(..., new_column_name=...) instead.

Autogenerate also misses server defaults, some constraint changes, and most index changes. Treat what it writes as a first draft.

Commit migration files to git. They are source code. The migrations/ directory is bind-mounted in development precisely so generated files land in your working tree.


Never edit a migration that has already run anywhere but your own laptop. Alembic records the current revision in an alembic_version table; rewriting applied history puts environments into states Alembic cannot reconcile. Write a new migration instead.

Write the downgrade . Autogenerate usually fills it in. Verify it, since it is what you will reach for at an inconvenient hour.

Useful commands:

```
docker compose run --rm web flask db current # applied revision
docker compose run --rm web flask db history # all revisions
docker compose run --rm web flask db downgrade # back one
```

## 9. Stage 7: Containerizing the app

Dockerfile :

```
FROM python:3.12-slim
ENV PYTHONDONTWRITEBYTECODE=1 \
PYTHONUNBUFFERED=1 \
FLASK_APP=wsgi.py
WORKDIR /app
RUN apt-get update \
&& apt-get install -y --no-install-recommends postgresql-client \
&& rm -rf /var/lib/apt/lists/*
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
RUN cp -r /app/app/static /opt/static-dist
RUN chmod +x entrypoint.sh
EXPOSE 5000
ENTRYPOINT ["./entrypoint.sh"]
CMD ["gunicorn", "--config", "gunicorn.conf.py", "wsgi:app"]
```

Copy requirements.txt before the source. Docker caches layers, and a

layer's cache is invalidated when its inputs change. Because dependencies are


installed before COPY . . , editing a Python file reuses the cached install layer. Copy everything first and every code change reinstalls every package.

PYTHONUNBUFFERED=1 makes Python write logs immediately instead of buffering, so docker compose logs shows output in real time rather than in delayed bursts.

--no-install-recommends and cleaning the apt lists keep the image small.

postgresql-client is here only for pg_isready , used by the entrypoint.

ENTRYPOINT and CMD together. The entrypoint always runs; the CMD is the default argument it executes at the end via exec "\$@" . That means

docker compose run --rm web flask db upgrade still waits for Postgres first,

then runs your command instead of gunicorn.

## The entrypoint

```
entrypoint.sh :
#!/bin/sh
set -e
echo "Waiting for PostgreSQL at ${POSTGRES_HOST:-db}:${POSTGRES_PORT:-5432}..."
until pg_isready -h "${POSTGRES_HOST:-db}" -p "${POSTGRES_PORT:-5432}" -U "${POSTGRES_
sleep 1
done
echo "PostgreSQL is ready."
if [ -d /opt/static-dist ]; then
echo "Syncing static files for nginx..."
cp -r /opt/static-dist/. /app/app/static/
fi
if [ -d migrations ]; then
echo "Applying database migrations..."
flask db upgrade
fi
exec "$@"
```

Three practices in fifteen lines:

set -e aborts on the first failing command. Without it, a failed migration would be logged and the server would start anyway, serving traffic against a schema that does not match the code.

exec "\$@" replaces the shell process with gunicorn, so gunicorn becomes PID 1 and receives SIGTERM directly from Docker. Without exec , the shell


stays PID 1, signals never reach gunicorn, and every shutdown takes the full ten-second timeout before Docker gives up and kills it.

The static sync exists for a non-obvious reason. In production, a named volume is mounted at app/app/static so nginx can read those files. A volume mount shadows whatever the image had at that path, so without this step nginx would serve an empty directory. The Dockerfile stashes a pristine copy at /opt/static-dist at build time and the entrypoint restores it on every start. That cp line in the Dockerfile looks removable and is not.

Note: a recent edit stripped the comment explaining this from the Dockerfile. The mechanism still works, but the next person to read it has no idea why that line exists.

## 10. Stage 8: Production with nginx and gunicorn

## Why the dev setup is not production

Three separate problems:

The Flask development server is not a production server. It is single-threaded by default, has no request limits, and its own documentation says not to deploy it. You need a real WSGI server.

WSGI is the interface between a web server and a Python application. Flask implements the application side; gunicorn implements the server side, running multiple worker processes that each handle requests.

Gunicorn alone still is not enough. It is excellent at running Python and mediocre at everything else a public-facing server does: serving static files efficiently, terminating TLS, buffering slow clients, enforcing request size limits. nginx handles all of that, and forwards only real application requests to gunicorn.


The slow-client problem is the subtle one. Gunicorn's default sync workers handle one request at a time. A client on a bad mobile connection sending a request body slowly occupies an entire worker for the duration. With three workers, a handful of slow clients stalls your whole application. nginx reads the complete request into a buffer first, then hands it to gunicorn all at once, so workers are only ever busy doing actual work.

## The WSGI config

```
gunicorn.conf.py :
bind = "0.0.0.0:5000"
workers = int(os.environ.get("GUNICORN_WORKERS", multiprocessing.cpu_count() * 2 + 1))
worker_class = "sync"
threads = int(os.environ.get("GUNICORN_THREADS", 1))
timeout = int(os.environ.get("GUNICORN_TIMEOUT", 30))
graceful_timeout = 30
keepalive = 5
max_requests = 1000
max_requests_jitter = 100
accesslog = "-"
errorlog = "-"
forwarded_allow_ips = "*"
```

Worker count of (2 × cores) + 1 is the documented starting point. Each worker is a separate process with its own memory and its own database connections, so more is not automatically better. Measure before tuning.

max_requests recycles workers after roughly a thousand requests. This is a pragmatic defense against slow memory leaks: rather than hunting a leak that grows over days, the worker is replaced before it matters. The jitter value randomizes the threshold so all workers do not restart simultaneously.

Logs to stdout and stderr, written as "-" . Containers should log to standard streams and let the platform collect them. Writing to files inside a container means logs vanish when the container is replaced.

forwarded_allow_ips = "*" tells gunicorn to trust X-Forwarded-*

headers. That is safe here only because gunicorn is unreachable except through nginx. If gunicorn were exposed directly, a client could forge its own IP in those headers.

## The nginx config


```
upstream flask_app {
server web:5000;
}
server {
listen 80;
server_name _;
server_tokens off;
client_max_body_size 10M;
location /static/ {
alias /app/app/static/;
expires 30d;
access_log off;
add_header Cache-Control "public";
}
location / {
proxy_pass http://flask_app;
proxy_set_header Host $host;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
proxy_redirect off;
proxy_connect_timeout 30s;
proxy_send_timeout 30s;
proxy_read_timeout 30s;
}
}
```

server web:5000 works because Docker Compose provides DNS for service names on a shared network. There is no IP address to configure.

Static files never reach Python. nginx serves them from disk and tells browsers to cache them for thirty days. A request that gunicorn never sees is a request that costs you nothing.

The forwarded headers matter. Without them, every request appears to come from nginx's container IP, so your logs, rate limiting, and any IP-based logic see one client. X-Forwarded-Proto is what lets Flask know the original request was HTTPS even though nginx forwarded it over plain HTTP internally.

server_tokens off stops nginx advertising its exact version in response headers and error pages, which is free hardening.


client_max_body_size caps upload size at the edge. The default is 1MB, which produces confusing 413 errors on file uploads.

## The production compose file

The important differences from development:

```
services:
web:
# No "ports:" — unreachable from outside Docker
volumes:
- static_files:/app/app/static # not a source bind mount
networks:
- backend
- frontend
db:
# No "ports:" either
networks:
- backend
nginx:
ports:
- "${HTTP_PORT:-8080}:80" # the only public port
networks:
- frontend
networks:
frontend:
backend:
internal: true
```

Only nginx publishes a port. In development, Postgres on 5432 and the app on 5001 are exposed to your whole local network. In production neither is reachable from outside Docker at all.

internal: true on the backend network blocks all external connectivity for containers attached only to it. The database is reachable by the app and by nothing else. The app straddles both networks, which is what lets nginx reach it while the database stays isolated.

No source bind mount. Development mounts .:/app so edits appear instantly. Production deliberately does not: the image is the artifact you tested and the thing you deploy. A bind mount would mean the running code is whatever happens to be on the server's disk.

Secrets are required, not defaulted:

```
SECRET_KEY: \${SECRET_KEY:?SECRET_KEY is required}
```


The :? syntax makes compose refuse to start if the variable is unset. This is the difference between a missing secret being a loud startup failure and it being a silent security hole where production runs on dev-secret-change-me .

restart: always rather than unless-stopped , so containers come back

after a host reboot.

## Before this faces the public internet (Some we will do it later)

This stack is production-shaped. Four things remain:

Add TLS. nginx listens on port 80 with no certificate. Everything,

including session cookies, crosses the network in plaintext. Terminate HTTPS at nginx and redirect HTTP to it.

Set a real server_name . The catch-all _ accepts any Host header, which

enables cache poisoning and host-header injection against a public server.

Use real secrets management. .env.prod is a plaintext file on disk. Use Docker secrets or your platform's secret store.

Back up the volume, and test a restore. An untested backup is not a backup.

Also worth adding before real traffic: rate limiting in nginx ( limit_req_zone ), a /health endpoint for container healthchecks, a non-root USER in the Dockerfile, and CSRF protection as noted in stage 4.

## 11. Good practices reference

A consolidated checklist of what this project demonstrates.

## Application structure

- Use an application factory; avoid a module-level global app.

- Keep extension instances in their own module to break circular imports.

- Group routes into blueprints, one per feature area.


- Reference routes with url_for , never hardcoded URL strings.

- Import models inside the factory so their tables register before migrations.

## Configuration and secrets

- Read all configuration from environment variables.

- Never commit secrets. Ship a .env.example with placeholders instead.

- Make production fail loudly on a missing secret rather than defaulting.

- Keep .env and .env.prod in .gitignore .

## Database

- Use migrations from the first commit; avoid db.create_all() .

- Read every autogenerated migration before applying it, especially renames.

- Commit migration files; never edit one that has already been applied.

- Use timezone-aware timestamps.

- Enforce constraints in the schema, not only in application code.

## Docker

- Pin base image tags; avoid latest .

- Copy the dependency manifest before the source to preserve layer caching.

- Use exec "\$@" in the entrypoint for correct signal handling.

- Use set -e so startup failures stop the container.

- Log to stdout and stderr.

- Use healthchecks with condition: service_healthy , not bare depends_on .

- Store persistent data in named volumes.

## Production

- Never run the Flask development server in production.

- Put a reverse proxy in front of the WSGI server.

- Serve static files from nginx, not from Python.

- Publish only the proxy's port; keep the app and database internal.

- Put the database on an internal: true network.

- Ship the image, not a bind mount of source code.

- Forward the real client IP and protocol headers.

- Recycle workers with max_requests to bound memory growth.

## Web application safety
